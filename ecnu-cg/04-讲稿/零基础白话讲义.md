# 零基础白话讲义：i3dgs 到底在做什么

> 给完全没有图形学基础的人看的一版解释。
> 读完这份，你能理解论文的**全部主要思想**，并能在台上讲 5 分钟。
> 不需要任何前置知识，只需要"照片是站在某个位置朝某个方向拍的"这一条常识。

---

## 0 先卸压

这篇论文的难点**不在图形学**。

图形学部分（3DGS 是什么、怎么渲染）在 2023 年就被别人做完了，这里只是拿来用。这篇论文真正做的事是**系统工程**：怎么让一整套流程在几毫秒内跑完、怎么让误差不乱跑、怎么让显存不炸。

所以你要讲的东西，本质上是三个日常问题：

1. 你要等多久才能看到结果？
2. 你随手拍的照片顺序乱七八糟，它还能不能用？
3. 你走回原地时，它会不会接不上？

想清楚这三个，你就讲清楚了 80%。

---

## 1 一句话说完 3DGS

> **3DGS 就是用几百万颗半透明的彩色光斑，把一个房间"堆"出来。**

每颗光斑只记五件事：**在哪儿、多大、朝哪边扁、什么颜色、多透明**。

从任何角度看过去，这些光斑按远近叠在一起，就糊成那个角度的照片。这就是"渲染"。

跟游戏里画三角形面片不同：它不建"墙面"，只堆光。好处是——**显卡天生擅长把一堆半透明的东西糊在一起**，一秒能糊一百多次；而且哪颗光斑不对，单独改它就行，不牵一发动全身。

**它怎么学会的？** 很朴素：

> 先把光斑瞎撒一片 → 从某个角度"看一眼"（画出图）→ 跟真实照片比 → 差在哪就往哪挪一点 → 重复几万次。

挪到最后，光斑就自己站到了正确的位置上。整个"学习"过程就是这个。

---

## 2 唯一必须懂的一件事：相机位置

上面那句"从某个角度看一眼"，**这个角度必须有坐标**。

相机站在哪（3 个数）、朝哪边（3 个数），合起来叫"**位姿**"（pose）。名字很专业，就是这两件事。

麻烦在于：你拍照时从来没记录过它。手机给你照片，不给你"我当时站在哪"。

**怎么反推？** 靠"同一个东西出现在两张照片里"。

- 第 1 张和第 47 张里都有同一把椅子腿；
- 第 1 张里它在画面右边，第 47 张里它在画面左边；
- 那么两台相机的相对位置只有一种摆法能让这两条视线对上。

把几百张照片两两都这么做，就能拼出整段拍摄的相机轨迹。这个活叫 **SfM**（Structure from Motion，从照片反推结构）。

**代价是什么？**
- 两两配对 → 照片越多越慢（几百张就是几万对）
- 必须**等所有照片到齐**才能开工

第二点是整篇论文的起点。**你在现场拍的时候，是不知道结果的。** 拍完回家传电脑、等十几分钟，才发现"这个角落没拍到""这里糊了"——白跑一趟。

## 3 这篇论文要解决的三个现实麻烦

| 麻烦 | 现场的感受 | 它的招 |
|---|---|---|
| **要等** | 拍完才知道成不成 | 边收边建，每来一张就算一点，300 多毫秒出一版 |
| **怕乱** | 随手拍的照片顺序是乱的 | 先用"整体像不像"粗筛，再仔细验证，不做两两全比 |
| **会漂** | 走十分钟回到起点，接不上，差半米 | 把误差像橡皮筋一样沿路径摊开 |

再加一招处理第四个麻烦：**场景太大，显卡装不下**。远处的光斑几个合成一个大的，走近了再拆开——就是地图 App 放大缩小的那个思路。

---

## 4 三个比喻，讲清三招

### 4-1 "怕乱"这招：先粗筛，再细看

有序的视频，第 i 张只跟第 i−1 张比就行，很省。但随手拍的照片不能这么干——第 300 张可能跟第 20 张拍到同一片地方。

如果两两全比，几百张就是几万对，算不完。

它的做法像**相册按相似度分组**：

1. 先把每张图压成一个"整体印象"（比如"这是个室内、有绿植、偏暖色"），比印象，从上千个候选里挑出 20 个最像的。这一步几乎不花钱。
2. 再在这 20 个里，用轻量的方法找共同点，筛到 5 个。
3. 最后才用最贵、最准的方法仔细验证，剩下的才算数。

**贵的那一步只用在一两对上**，这就是"乱也能快"的全部秘密。

> 术语：这三步分别叫"视觉位置识别 / 局部特征匹配 / 几何验证"。论文消融显示，去掉第一步，质量从 26.29 dB 掉到 24.78 dB——是影响最大的一环。

### 4-2 "会漂"这招：橡皮筋（全文最漂亮的一手）

先说漂是怎么来的。

你边走边建，每一张新照片都只跟"刚才那几张"对齐。每一次对齐都有一点点误差，而这些误差会**累积**——就像蒙着眼睛走路，每一步都偏一点点，走十分钟就偏出去一大截。

于是会有这一幕：你绕了一圈回到起点，重建结果却显示"你还没回到起点，差半米"。

**传统做法**：发现接不上，就把所有照片重新算一遍。准，但要几分钟——实时性直接归零。

**它的做法**：不去重算，而是把这半米的落差**摊回到整条路径上**。

想象一根橡皮筋：
- 它的两头要接到一起，但差了一截；
- 你不要把某一头硬拽过去（那会让局部全扭曲）；
- 而是让橡皮筋整体均匀缩短一点点——每一段只挪那么一丁点，两头就自然对上了。

它就是这么干的：在路径上找一条"最可信的主干"，然后按距离把修正量摊下去，离接口近的多摊一点，远的少摊一点。

**结果**：代价从几分钟变成几毫秒，精度只损失一点点。

而且光斑怎么办？每颗光斑出生时记住了"我是跟着哪张照片来的"，修正时直接套用那张照片的位移就行——几百万颗光斑不用一颗颗改。

> 术语：这一步叫"回环闭合 + 图传播"。核心公式（Sim(3)）的意思是"旋转 + 平移 + 缩放"的组合，因为单目重建本来的尺度就是不确定的，必须允许缩放。

### 4-3 "装不下"这招：远了合并，近了拆开

场景一大，光斑数量线性增长，显存会炸（论文里 4050 张的场景，跑到第 795 张就没内存了）。

它的办法跟游戏里的 LOD 一样：
- 某个光斑在画面里小到小于半个像素、而且这种小光斑占了很大比例 → 就把附近的 4 颗合并成一颗大的，原来的存到内存里去；
- 你走近了、它变大到超过 1 个像素 → 再把子光斑取回来。取的时候偷偷在后台做，避免卡顿。

效果：4050 张的场景，峰值控制在 370 万颗光斑、12.8 GB 显存以内。

## 5 术语翻译表（30 个，被问到就翻这个）

| 论文里的词 | 其实是在说 |
|---|---|
| 3DGS / 三维高斯泼溅 | 用几百万颗半透明彩色光斑堆出场景 |
| 高斯（Gaussian） | 一颗光斑（位置、大小、朝向、颜色、透明度） |
| 泼溅（splatting） | 把光斑投影到屏幕上叠起来 |
| 光栅化（rasterization） | 把 3D 东西画到 2D 屏幕上的过程 |
| 辐射场（radiance field） | 一个"从任何角度看都长这样"的场景表示 |
| 新视角合成（NVS） | 从没拍过的角度生成照片 |
| 位姿（pose） | 相机站在哪 + 朝哪边 |
| 内参 / 外参 | 相机自己的参数（焦距）/ 相机在世界里的位置朝向 |
| SfM | 从照片反推相机位置和场景结构 |
| COLMAP / GLOMAP | 两个做 SfM 的现成工具 |
| 特征点 | 照片里好认的点（角、边交点） |
| 匹配 / 内点（inlier） | 两张照片里找到同一个东西 / 匹配得对得上号的那些点 |
| RANSAC | 一种"先随便猜、再投票剔除错答案"的稳健算法 |
| 三角化（triangulation） | 用两条视线交叉算出一个点的 3D 位置 |
| BA（光束法平差） | 一起微调所有相机位置和 3D 点，让整体误差最小 |
| 局部 BA | 只挑一部分相机一起微调，省时间 |
| Schur 补 | 一种解大型方程组时"先消掉一部分未知数"的技巧 |
| 雅可比（Jacobian） | 描述"参数动一点，误差会怎么变"的矩阵 |
| 关键帧（keyframe） | 被选中参与计算的代表帧，不是每张都用 |
| 协视图（covisibility graph） | 一张关系网，记录"哪两张照片拍到了同一片地方" |
| 回环 / 回环闭合 | 走回原地发现接不上，把误差摊回去 |
| 漂移（drift） | 误差随采集时间一点点累积 |
| 图传播 | 沿着关系网把修正量摊给所有节点 |
| Dijkstra | 找图上最短路径的经典算法 |
| 测地距离 | 图上的距离（要走几条边、边权多少），不是直线距离 |
| Sim(3) | 旋转 + 平移 + 缩放 的组合变换 |
| 6D 旋转表示 | 一种避免"万向锁"的表示旋转的方法 |
| 渐进式层级 / LOD | 远了合并、近了拆开 |
| KL 散度 | 衡量两个分布差多少，这里用来判断两颗光斑能不能合并 |
| PSNR | 重建图跟真照片有多像，越高越好（26 dB 左右算不错） |
| SSIM / LPIPS | 另外两个"像不像"的指标 |

## 6 上台怎么讲：零基础版 5 分钟口径

如果你觉得原来的 12 分钟讲稿太重，就用这个版本。**全程不出现公式，只讲因果。**

> **（30 秒）开场**
> 3DGS 出图很漂亮，但它有个前提：你得先知道每张照片是在哪拍的。这篇论文把这个前提拆掉了。
>
> **（60 秒）先讲清 3DGS**
> 它不建模型，它是用几百万颗半透明彩色光斑把场景"堆"出来。从任何角度看，这些光斑叠在一起就是那个画面。所以它快——显卡天生擅长糊这种东西。
>
> **（60 秒）讲清痛点**
> 但它要先知道自己站在哪。这个"位置"没法从照片直接读出来，得把所有照片两两比对、反推出来。这一步有两个代价：慢，而且必须等照片全部到齐。
> 于是你在现场拍的时候，是不知道结果的。拍完回家等十几分钟，才发现有个角落没拍到。
>
> **（90 秒）讲它的招**
> 它做了两件事。
> 第一，每来一张新照片就算一点，不等到最后。为了做到这个，它不两两全比——先用整体印象粗筛出 20 张，再用轻量的方法筛到 5 张，最后才仔细验证。贵的那一步只用在一两对上。
> 第二，边走边建误差会累积，走回原地会接不上。传统做法是全部重算，要几分钟。它不重算，而是把这点落差像橡皮筋一样摊回整条路径——每段挪一点点，接口就对上了。代价从几分钟变成几毫秒。
>
> **（45 秒）讲结果**
> 效果是：一个场景一分多钟出 26 dB 的重建，比离线方案快将近七倍、质量只差 1 dB 出头。把输入顺序完全打乱，只掉 0.5 dB——说明它不是勉强能用，是真的吃乱序。
>
> **（45 秒）讲我们做的**
> 我们自己把它从零跑起来了：185 张无序照片，不给任何相机位置的先验，62 秒完成，25.95 dB，导出了一段可以自由漫游的视频。踩了 12 个坑，真正要改代码的只有 3 处——这也说明论文的算法本身是扎实的，卡住人的是工程环境。

被追问细节、你确实答不上来时，用这三句，**不要硬编**：

1. **"这一块我没有追到实现层面，从论文的描述看，它是在做 X。"**

   （主动交代口径，比被人抓出来强得多）

   （当你被问"那它这个缺陷怎么办"，把球踢回论文）

## 8 你现在应该能回答的三个问题（自测）

1. 为什么 3DGS 必须先知道相机位置？（答：因为要"从那个角度看一眼"才能算误差）
2. 为什么"边走边建"会越走越偏？（答：每次对齐的误差会累积）
3. 它凭什么不用重算就能修正回环？（答：把误差沿最可信的路径摊开，而不是重新解一遍）
