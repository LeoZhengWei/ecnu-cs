# 自拍场景重建实录：实验室两台人形机器人

> 用 i3dgs 重建**自己手机拍的**一组乱序照片，验证论文的三条核心能力：
> 无序输入、免位姿、免内参、即时出结果。
>
> 算力：`172.88.88.14`，单张 RTX 4090 24 GB（4 卡共用）
> 日期：2026-10-29

---

## 一、结论先看

> **85 张微信下载的乱序照片，没给位姿、没给内参，直接喂进去，55 秒后出来一个能自由漫游的三维场景。**

这不是数据集上的评测，只是一次真实使用的验证。所以下面把"证明了什么"和"证明不了什么"分开写。

| 指标 | ds=2（640×853） | ds=1（1280×1707，成片） |
|---|---|---|
| 关键帧 / 输入 | 76 / 85 | **81 / 85** |
| 高斯数量 | 471,902 | **1,857,881** |
| 流式重建耗时 | 30.9 s（2.75 FPS） | **54.9 s（1.55 FPS）** |
| 峰值显存 | 4.86 GB | **8.45 GB** |
| PSNR / SSIM / LPIPS（留出 1/6 帧） | 20.76 / 0.665 / 0.293 | 19.47 / 0.611 / 0.349 |
| 内参（焦距） | 初值 896 → 收敛 **1209.8** | 同 |

**PSNR 为什么全分辨率反而更低**：19.47 < 20.76 不是"全分辨率更差"。PSNR 是逐像素平均误差，分辨率翻倍后高频细节多得多，误差更难压。视觉上 ds=1 明显更清晰（龙门架、笔记本、远处人头模型在半分辨率下是糊的）。**看画质别只看 PSNR。**

## 二、输入是什么

| 项 | 数值 |
|---|---|
| 原始文件 | 87 张微信 JPG，共 28 MB |
| 像素尺寸 | 85 张 1280×1707（竖拍）+ 2 张 960×1280 |
| 清晰度（Laplacian 方差） | 中位 628，最低 50（最糊的两张恰是那 2 张异尺寸的） |
| 实际使用 | **85 张** |

**预处理只做两件事**，都记录在案：

1. **剔除 2 张 960×1280**。原因不是糊，而是**尺寸和其他 85 张不同**——`image_dataset.py:88-89` 只读第一张图的宽高，全场共用一个相机模型，混尺寸会直接错位。这 2 张同时最糊，剔除无损失。
2. **按序号重命名** `img_0001.jpg … img_0085.jpg`。原文件名含 `&`、`=`、`@`，在 shell 和 scp 里是特殊字符，重命名只是消除隐患。

**没有做的**：没有缩放、没有重新编码（`shutil.copyfile` 原字节复制，画质零损失）；**尤其没有排序**。

> 保留的就是微信 `MsgID` 的随机顺序——这恰好是一次**真实的「无序输入」测试**。
> 之前 garden 那次用的是有序视频序列，只能说明"没给 COLMAP 先验"，不构成无序证据；这次才是。

## 三、为什么乱序能直接跑通

不是靠"先把照片排成序"，而是**顺序在这套流程里根本不参与决策**：

- 初始化不是"从第一帧开始逐帧长"。先到的若干帧先放进 **bootstrap 候选池**（`train.py: try_bootstrap_from_shelf`），
  算池内两两 VPR 余弦相似度，挑**最相似的一对**，验证 2D 匹配数 ≥ 400，再贪心地把最相似的帧加进这个簇。
- 之后每个新帧的邻居来自"整段历史里长得像的帧"（视觉检索 + 协视图），不是"上一帧"。

轨迹数据也印证了：81 个关键帧绕两台机器人走了一圈，但**相邻关键帧平均跳 0.470、最大 2.415（5 倍跳变）**——
是"跳着看"，不是顺着走，几何仍保持全局一致。

## 四、漫游视频怎么来的（这里有一个坑）

`robotlab_walkthrough_8s.mp4`：1280×1706，240 帧 / 8 秒，**一条全新的相机轨迹**，不是原照片回放。

### 坑：直接用 `render_path.py` 会退化成"照片快切"

作者的 `render_path.py` 要的是**一条新相机路径**（我想让相机从哪些位置看这个场景）。
最初误把 `sparse/0`（训练时拍照的位姿文件）传了进去，于是渲染相机与拍照相机一一重合——
81 帧等于把 81 张原照片按文件顺序各重画一遍，帧序又是乱的，相机在房间里乱窜，观感就是"帧拼接播放"。

| | 相邻帧相机平均位移 | 最大 | 总路程 |
|---|---|---|---|
| 旧（文件序 81 帧） | 0.365 | 1.769 | 29.24 |
| 新（方位角序重采样 240 帧） | **0.022** | 0.039 | 约 5.0 |

### 修法：自写轨迹生成（`orbit_render.py`，未改动作者代码）

| 步骤 | 做法 |
|---|---|
| 竖直方向 | 相机中心点云 **PCA 最小主轴**（不能逐帧平均相机 up，手持横滚太噪） |
| 场景中心 | 81 条视线的射线最小二乘交点 |
| 可用弧段 | 按方位角排序后找最大空洞（29.1°），沿补集 **319°** 走 |
| 重采样 | 等角度 **240 帧**，角速度恒定 |
| 平滑 | 半径/高度做窗口 9 移动平均（原始半径 0.50~1.23 → 平滑后 0.73~1.14） |
| 安全约束 | 位置**夹在训练相机之间**（中位偏移 7.6 cm），避免看到未观测区域 |

### 三条"这不是照片回放"的证据

1. **两台机器人在画面里左右对调**——开头橙色在**右**（`evidence/02_orbit_frame_0000.jpg`），第 5 秒橙色在**左**（`evidence/03_orbit_frame_0120.jpg`），中间连续过渡。
   照片按序播放**不可能**产生这种画面。
2. 出现了原照片没有的角度：黑色机器人**正后方**、橙色机器人**侧面**。
3. 同点横移 5 cm 的视图有物理正确的视差（近处位移大于远处）。

## 五、边界：哪些事这次证明不了

**必须知道的四条：**

1. **没有 COLMAP 真值 ⇒ 位姿误差测不了。** 能算的只有留出视角的图像质量（渲一张 vs 真照片）；
   论文里 `R°0.155 / t 1.888` 那种数字需要 `--eval_poses` 对齐真值。**写报告时这个场景不能写位姿精度。**
2. **PSNR 不能和论文比。** 论文 MipNeRF360 是 26.29 dB，这里 19.47 dB——不同场景、不同分辨率、
   不同评测协议，放在一起比没有意义。这次的价值在"能跑通"，不在"分数高"。
3. **相机会被视角边界卡住。** 试过抬到 **44° 俯视**（`evidence/04_topdown_44deg_limit.jpg`）：主体几何完全正确
   （两台机器人立着、脚垫与吊架关系都对），但**天花板和背景墙糊成一片**——这些面在整个采集中只被单方向观测过，
   视角一变高斯就被拉长。所以运镜必须限制在训练相机的包络内部。这是论文承认的"覆盖不足无法凭空补出几何"。
4. **场景本身的动态因素**：机器人是吊着的可能微动（会产生局部重影），背景有走动的人和会被推开的椅子
   （动态物体无法建模，会被摊平成一团）。橙色外壳高反光、黑色亮面也不满足朗伯假设。

**一条反直觉的**：VPR 模型论文写的是 MixVPR，代码实际用 **MegaLoc**
（`scene/vpr_model.py` 里留着作者注释 `# Use MegaLoc instead of MixVPR for licensing reasons`）。以代码为准。

## 六、复现步骤

```bash
# 一、本地预处理（剔除异尺寸 + 重命名，不重编码）
python user_demo/preprocess.py

# 二、上传 85 张到服务器
ssh hjadmin@172.88.88.14 'mkdir -p /datafast/zhengwei-i3dgs/data/robotlab/images'

# 三、重建（run_scene14.sh 会做尺寸一致性硬检查、自动挑最空的卡、显存不足自动加大降采样）
bash /home/hjadmin/zhengwei/i3dgs-demo/scripts/run_scene14.sh \
     --scene-path /datafast/zhengwei-i3dgs/data/robotlab \
     --name robotlab --ds 1

# 四、渲染新轨迹（不是 render_path.py，那条路会退回成照片回放）
python scripts/orbit_render.py --result <result_dir> --mode smooth --frames 240
```
